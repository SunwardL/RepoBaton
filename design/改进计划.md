# RepoBaton 可编排协作与原生会话改进计划

## 目标与使用方式

把 RepoBaton 建设为本地多 Agent 协作工作台。用户在页面上安排步骤、选择 Agent 与模型、编写角色提示词，并决定怎样交接结果。RepoBaton 负责按流程执行、展示状态、记录交接信息和支持人工介入。

例如，一个任务可以依次由 Claude 设计方案、Codex 实现、另一个 Claude 会话检查交互，最后等待用户确认。另一个任务可以只安排代码修改和文档更新，然后由用户查看工作区。

Agent 使用各自的原生会话管理上下文。不同会话不会自动共享对话内容，流程需要明确交付任务要求、前一步输出或指定文件。共享工作区的串行步骤可以看到之前步骤留下的文件改动。

## 范围和原则

- 保持 Windows 本机、单用户、多项目的使用方式。同一仓库一次执行一个任务，不同仓库的任务可以并行。
- 第一版自定义流程在一个任务的同一个 worktree 中串行执行。每个步骤选择自己的 Agent、模型、角色提示词和工作区权限。
- 可视化配置是主要入口。YAML 用于可选的导入、导出与复用，导入先预览并明确保存。
- Git 提交、命令执行、审批和远端发布由流程或用户明确选择。支持不创建提交的工作方式。
- 原有四阶段流程作为内置模板保留，现有用户和历史任务继续可用。原生会话仅管理 RepoBaton 发起的会话。
- 不同 Agent 的上下文隔离。每一步的输入由流程显式指定，不能假设其他 Agent 看过同一段对话。

## 改造前的基础与已知问题

- 当前阶段类型和顺序固定为规划、实现、审核、发版草稿，包含测试、审核返修和可选发布。页面可以更换各阶段使用的 Agent 和模型。
- 项目已有全局 Agent 配置、任务级选模、按仓库限制执行、计划审批、检查点恢复和运行记录。
- 各阶段调用已记录原生会话信息，任务详情可复制会话 ID 和继续命令。README 记录了 Windows 上 CLI 按 ID 恢复的验证，Codex 桌面客户端显示尚未确认。
- 第一期的三项可靠性问题已修复并有回归测试（见下方“第一期”的进展）。
- 目前 Git 提交、审核结论与实现循环依赖固定阶段和数据结构。自定义流程需要兼容这些已有语义。

## 第一期：可靠性与原生会话

**目标：** 在扩展流程前修复现有行为，让用户能找到并续接 RepoBaton 发起的原生会话。

### 实施内容

1. 修复默认 Agent 未改变时备用 Agent 丢失的问题，验证任务级覆盖和已有回退行为。
2. 尽可能在 CLI 报告会话 ID 时记录，覆盖失败、取消和超时；无法获取 ID 时如实显示原因。服务中断后的调用状态应与任务状态一致。
3. 根据实际使用的 CLI 启动方式生成继续命令，处理自定义路径和 Windows 路径引用。
4. 在 Windows 上用真实 Codex 和 Claude Code 验证通过会话 ID 恢复、worktree 关联与会话内容可见性，并确认 Codex 桌面客户端的实际表现。页面只承诺验证过的入口。
5. 保留旧任务详情和产物。历史记录缺少会话 ID 时明确提示。第三方 API 展示 RepoBaton 的事件与结果。

### 验收条件

- 默认工作流中的备用 Agent 在主 Agent 失败时按配置接手。
- 成功和已获得 ID 的异常调用均能在任务详情中找到对应会话，自定义 CLI 路径生成的命令可运行。
- 服务重启后会话记录可读取，旧任务正常展示；中断记录不会一直误显示运行中。
- 实际验证 Codex 和 Claude Code 的 CLI 恢复，并记录桌面客户端是否显示相应会话。

**补充验证（2026-11-24）：**经用户授权，在一次性 Git 仓库中分别通过 RepoBaton 的真实 Codex CLI 和 Claude Code 适配器创建会话，再在相同 worktree 用会话 ID 续接，两者均正确复述上一轮的随机短码。没有写入用户项目或远端。Codex 桌面端会话索引的历史列表没有返回本次 Codex CLI 会话；由于检查时一次性项目已清理，尚不能据此断定桌面端在项目打开时是否显示该会话。

再次核对时，本机仍有该 Codex CLI 会话文件和工作目录元数据；应用的活动与归档会话列表均未返回该会话，但应用的会话读取接口能通过 ID 读到该会话及其两轮记录。记录的临时工作目录已不存在，因此这能确认应用后端可以读取会话，但不能断定目录仍存在时侧边栏是否显示它。

**界面补充验证：** 使用隔离临时项目和模拟的未确认 Claude 会话，在浏览器看到相应提示；分别点击“复制会话 ID”和“复制继续命令”均显示“已复制”。本次检查验证界面反馈，命令格式由自动化测试覆盖，没有调用模型。

**Windows 继续命令验证：** 将为 Codex 和 Claude 生成的命令分别输入真实 CMD，使用路径含空格的临时工作区和模拟 CLI，确认进入正确目录并传入相应的续接参数；没有调用模型。

**真实 Codex 中断补充验证：** 经用户授权，续接此前的测试会话，约 2.5 秒后取消；适配器返回 `cancelled` 错误并保留原会话 ID。该 ID 是续接参数，不是本次从新 `thread.started` 事件发现的 ID，不能据此验证后一种情况。

**真实 Codex 新会话中断：** 经用户再次授权，在隔离临时目录发起一次新会话，收到 `thread.started` 的 ID 后取消。任务标记为已取消，步骤标记为结果未知；从状态文件重新读取时，步骤和会话记录均保留该 ID。临时任务目录已清理。

该新会话可被桌面应用接口按 ID 读取，但不在活动或归档会话列表中；临时恢复其原目录后再次查询仍未列出。这个检查针对应用接口与空目录，不能保证每种项目和桌面界面的表现。

## 第二期：可视化串行工作流

设计一页纸：[第二期-可视化串行工作流设计.md](./第二期-可视化串行工作流设计.md)。要点：内置四阶段继续走原有 `Pipeline`，自定义流程用新的串行执行器；产物落盘并脱敏，引用只能向前且缺失时在启动前报错；结果未知的步骤不自动重跑；无提交流程下清理必须拒绝丢弃未提交改动；命令类 Agent 不得被称为只读；YAML 导入先预览命令、每次启动前确认，暂不做持久信任。


**目标：** 用户无需编辑 YAML，就能创建、保存和运行自己的串行流程。

### 实施内容

1. 提供流程编辑页面，支持添加、删除、排列步骤，编辑名称和提示词，为每个 Agent 步骤选择已配置的 Agent、模型和只读或可写权限。
2. 支持 Agent 步骤、命令步骤和人工确认步骤。用户能在开始前看到步骤顺序、工作区和执行所需配置。
3. 允许步骤选择需要的输入，包括任务描述、指定前序步骤输出和工作区文件。记录每一步输出及交接关系，并在页面查看。
4. 提供明确的 Git 选项：保留未提交改动、由流程中显式的提交步骤提交，或让 Agent 按提示词处理 Git。保留现有流程的自动提交行为作为内置模板的一部分。
5. 将现有四阶段流程提供为内置模板。保持原有计划审批、测试、审核返修、提交和发布规则，兼容原配置、历史任务和恢复入口。自定义流程的执行数据应标识其类型和版本，运行时保存所用配置快照。
6. 提供可选的 YAML 导入导出。导入前校验并展示预览，保存后生效。具体字段格式在实现设计中确定。
7. 从任务详情查看每一步状态、Agent、提示词、结果、会话和工作区变化。执行出错时明确显示失败步骤和可用的恢复操作。

### 验收条件

- 不编辑 YAML，用户即可创建三步流程，安排不同 Agent 角色和提示词，保存后重新打开并执行。
- 后续步骤能收到用户选定的前序输出，在同一 worktree 看见前一步文件修改。不同原生会话之间的交接内容可检查。
- 不提交 Git 的流程能完成并保留可查看的工作区改动。显式提交步骤能生成提交，未选择远端操作时不执行远端发布。
- 命令步骤、人工确认步骤和失败步骤能显示状态，并按所选操作继续。
- 现有四阶段模板、已有项目配置、旧任务查看和恢复的行为经回归测试保持可用。
- 任务运行中编辑模板或全局配置，不改变该任务已保存的流程选择；中断恢复使用任务的流程快照。
- 验证 YAML 导入预览、保存与导出，以及无效配置的错误提示。

- 中断提交的恢复还会检查分支和工作区：即使提交和暂存树匹配，若分支已变、缺少分支记录，或有未暂存修改、未跟踪文件，仍保持结果未知并提示核对。
- 人工重试结果未知的提交前，要求 HEAD、分支和暂存树匹配中断记录，且工作区没有未暂存或未跟踪文件，也没有 Git 操作或索引锁；否则保持暂停，避免重试时重新暂存其他改动。
- 已发生的提交因现场不干净而停在结果未知时，可在整理现场后重新核验：分支、父提交、树、暂存区和工作区全部匹配才继续，不会再执行提交。执行器及接口测试已覆盖。
- 提交树不匹配时可查看预期和实际提交的差异，显式确认接受；确认时重新检查分支、父提交、工作区与预览指纹，不会再次提交。执行器、接口和 Chrome 已验证，差异过长时提示用户在工作区检查完整内容。
- 普通目录由多个暂停任务共享时，人工接管其中一个会阻止同目录其他任务接管或继续；交还后可继续执行。独立测试已验证服务重启后该保护仍生效。
- 补充验证了工作区丢失和审批产物被改动：前者暂停且不重建，后者拒绝审批，均不会启动后续 Agent。
- 第三方 API 调用会把取得的密钥加入现有按值脱敏，即使环境变量名不含 `KEY` 或 `TOKEN`。本地模拟 OpenAI 和 Anthropic 兼容服务返回密钥的错误时，两者均不会暴露测试密钥；现有按值规则仅注册至少 6 个字符的值。
- 用隔离本机模拟服务执行了实际自定义任务，服务将上述非标准变量名的测试密钥回显在错误中；任务状态文件、事件和报告均未出现该值。
- Agent 已完成但步骤输出保存失败时，会话保留“已完成”和会话 ID，步骤单独标记为结果未知，避免把产物保存错误误报为 Agent 调用失败。
- 备用 Agent 接手后，步骤详情显示实际执行者与原配置，不把主 Agent 的模型误显示给备用 Agent；已用两个模拟命令 Agent 和浏览器验收。
- 使用真实本地命令 Agent 验证：任务在确认步骤暂停后，即使流程提示词、当前 Agent 命令和模型被修改，恢复执行仍采用任务快照中的原值。
- 离线打包项目和本机已有的 `yaml` 依赖，在隔离目录通过 `npm install --offline` 实际安装；从安装后的 CLI 启动服务，页面、静态资源和普通目录自定义流程预览均可用。另一次从安装包启动服务后，实际执行了普通目录中的命令步骤并验证产物。检查没有从网络安装依赖，也没有发布包。
- 补充测试了内置流程的人工接管：未提交改动会阻止继续；用户提交并再次交还后，旧审核标记为已过时，新的提交经过测试和审核。

- 自定义 Agent 或命令步骤的结果为 `unknown` 时，可在核对后提供输出并标记完成；命令步骤还需提供实际退出码。系统记录结果来自人工确认，不重复执行该步骤；提交及远端操作仍须遵守各自的核对规则。执行器和 API 测试已覆盖；真实 Chrome 中验证了填写退出码、勾选确认、提交后步骤标记及后续确认步骤收到人工输出。

- 自定义任务详情提供复制工作区路径和“打开工作区”按钮。已在隔离普通目录中通过真实 Chrome 点击按钮，并确认 Windows 文件管理器打开了对应目录。

## 第三期：人工接管与安全恢复

**目标：** 用户可以在 RepoBaton 和原生工具之间交接，恢复时能看清实际工作区状态。

### 实施内容

1. 在任务空闲或暂停时展示工作目录、会话 ID 和继续方式，用户可标记进入人工接管。
2. 接管期间暂停该任务的自动继续。交还时展示当前分支、新提交和未提交改动，由用户选择如何继续。
3. 检查点记录步骤状态、输入和输出及必要的工作区状态。恢复前校验现场，对已经完成或结果不确定的命令、提交与远端操作分别处理。
4. 人工修改或提交之后，现有模板中的测试和审核应针对实际变更重新执行；保留历史审核与其对应提交。自定义流程按用户配置的后续步骤继续。
5. 保留计划版本绑定、审批防重入、远端操作核对和同仓库执行限制。自定义流程若包含人工确认，需要针对用户实际查看的内容进行确认。

### 验收条件

- 运行中的任务不能同时进入人工接管；接管、修改和交还后，页面正确反映工作区现场。
- 未提交改动、工作区移动、会话缺失或外部状态不确定时，任务停在可处理状态并说明原因。
- 中断恢复不会静默重复执行结果未知的命令、提交或远端操作。
- 同仓库任务限制、审批版本检查和远端核对的现有回归测试继续通过。
